# Snapp Pay Data Pipeline — Data Cleaning and Transformation Rules

## 1. هدف سند

این سند قوانین پاک‌سازی و تبدیل داده را در پایپلاین Snapp Pay توضیح می‌دهد.

داده‌های ورودی از فایل‌های CSV و XLSX چند منبع تجارت الکترونیک دریافت
می‌شوند. ساختار ستون‌ها، نوع داده، شیوهٔ نوشتن متن فارسی، واحد قیمت،
وضعیت موجودی، URL، برند، دسته‌بندی و فروشنده در منابع مختلف یکسان نیست.

هدف مرحلهٔ Cleaning و Transformation این است که داده‌ها پیش از ورود به
لایهٔ تحلیلی، در یک ساختار استاندارد در جدول زیر آماده شوند:

```text
staging.stg_product_listings
```

اصل طراحی این پروژه این است که پاک‌سازی باعث حذف خاموش داده‌ها نشود.
دادهٔ اصلی در لایهٔ `raw` نگه‌داری می‌شود، دادهٔ استانداردشده در
`staging` ذخیره می‌شود و موارد مشکوک یا ناسالم در لایهٔ `audit` ثبت
می‌شوند.

---

## 2. جایگاه Cleaning در پایپلاین

ترتیب کلی پردازش داده به شکل زیر است:

```text
Raw CSV/XLSX files
        |
        v
Extract
        |
        v
raw.raw_file_registry
raw.raw_product_records
        |
        v
Cleaning and Transformation
        |
        v
staging.stg_product_listings
        |
        v
Validation, duplicate detection, outlier detection
        |
        v
audit tables + core dimensional model
```

مرحلهٔ Transform وظیفه دارد ستون‌های متفاوت منابع را با استفاده از
Mappingهای تعریف‌شده به ستون‌های استاندارد تبدیل کند.

---

## 3. اصول کلی پاک‌سازی

قوانین اصلی این پروژه عبارت‌اند از:

1. مقدار خام یک رکورد در `raw.raw_product_records.raw_payload` حفظ می‌شود.
2. مقادیر خالی، نامعتبر یا غیرقابل تبدیل به‌صورت کنترل‌شده به `NULL` تبدیل
   می‌شوند؛ نه به مقدار ساختگی مانند صفر یا رشتهٔ خالی.
3. تبدیل داده نباید اطلاعات مهم را بدون ثبت یا دلیل حذف کند.
4. داده‌های مشکوک مانند قیمت صفر، قیمت ناموجود، تکراری یا پرت، برای تحلیل
   کیفیت داده Flag می‌شوند.
5. تمام قیمت‌های استانداردشده با کد ارز `IRR` در Staging و Core ذخیره
   می‌شوند.
6. فیلدهای متنی برای جست‌وجو، Match کردن و تولید Business Key نرمال‌سازی
   می‌شوند.
7. مقادیر اصلی مانند نام خام برند، دسته‌بندی و فروشنده تا حد امکان در
   ستون‌های `*_raw` حفظ می‌شوند.

## 4. Mapping ستون‌های منابع

منابع داده ساختار یکسانی ندارند. به همین دلیل فایل زیر مسئول تعریف
Mappingهای منبع‌محور است:

```text
src/source_mappings.py
```

هدف Mappingها این است که ستون‌های هر فایل به ستون‌های استاندارد زیر
منتقل شوند:

| فیلد استاندارد | توضیح |
|---|---|
| `source` | کد منبع، مانند `torob` یا `snapp_pay` |
| `dataset` | نام Dataset یا فایل ورودی |
| `source_id` | شناسهٔ محصول یا Listing در منبع، در صورت وجود |
| `product_title` | عنوان محصول |
| `brand_raw` | نام برند در دادهٔ منبع |
| `category_raw` | نام دسته‌بندی در دادهٔ منبع |
| `merchant_name_raw` | نام فروشنده یا Merchant در دادهٔ منبع |
| `price` | قیمت فعلی استانداردشده |
| `old_price` | قیمت قبلی یا قیمت قبل از تخفیف |
| `discount_percent` | درصد تخفیف |
| `cash_back_percent` | درصد کش‌بک |
| `availability_raw` | مقدار خام وضعیت موجودی |
| `is_available` | وضعیت موجودی استانداردشده |
| `product_url` | URL صفحهٔ محصول |
| `image_url` | URL تصویر محصول |
| `search_keyword` | کلیدواژهٔ جست‌وجو، در صورت وجود |
| `source_price_unit` | واحد قیمت اولیه، در صورت تشخیص |
| `currency_code` | کد ارز استاندارد، `IRR` |

## 5. پاک‌سازی مقادیر خالی

### 5.1 مسئله

منابع مختلف ممکن است مقدار خالی را به شکل‌های زیر ثبت کنند:

```text
NULL
NaN
None
""
" "
"N/A"
"NA"
"null"
"-"
```

وجود این مقادیر به‌صورت رشته باعث خطا در Validation، محاسبهٔ قیمت و
گروه‌بندی می‌شود.

### 5.2 قانون

اگر مقدار یک فیلد متنی یا عددی معادل مقدار خالی باشد، به `NULL` تبدیل
می‌شود.

### 5.3 نتیجه

- رشتهٔ خالی به‌عنوان عنوان محصول معتبر تلقی نمی‌شود.
- قیمت خالی به `NULL` تبدیل می‌شود.
- نام Merchant یا Brand خالی به‌صورت `NULL` ذخیره می‌شود.
- URL خالی در ستون URL ذخیره نمی‌شود.
- وضعیت موجودی ناشناخته به‌صورت `NULL` باقی می‌ماند.

### 5.4 مثال

| مقدار خام | مقدار استاندارد |
|---|---|
| `""` | `NULL` |
| `"   "` | `NULL` |
| `"N/A"` | `NULL` |
| `"null"` | `NULL` |
| `NaN` | `NULL` |

## 6. نرمال‌سازی متن فارسی و عربی

### 6.1 مسئله

عنوان کالا، برند، دسته‌بندی و نام فروشنده ممکن است با ترکیبی از
کاراکترهای فارسی، عربی و انگلیسی نوشته شده باشند. برای مثال، دو مقدار
ظاهراً مشابه ممکن است در Unicode متفاوت باشند و در Join، Group By،
Duplicate Detection یا جست‌وجو به‌عنوان دو مقدار مجزا شناخته شوند.

### 6.2 تبدیل کاراکترهای عربی به فارسی

کاراکترهای رایج عربی به معادل فارسی تبدیل می‌شوند.

| مقدار خام | مقدار نرمال‌شده |
|---|---|
| `ي` | `ی` |
| `ى` | `ی` |
| `ك` | `ک` |
| `ة` | `ه` |
| `ۀ` | `ه` |
| `ؤ` | `و` |
| `أ` | `ا` |
| `إ` | `ا` |

### 6.3 نرمال‌سازی فاصله

موارد زیر پاک‌سازی یا استاندارد می‌شوند:

- فاصله‌های چندگانه.
- Tab.
- Line break.
- Non-breaking space.
- فاصلهٔ ابتدا و انتهای متن.
- کاراکترهای کنترلی یا نامرئی که در Match کردن مشکل ایجاد می‌کنند.

پس از نرمال‌سازی، فاصله‌های متوالی به یک فاصلهٔ معمولی تبدیل می‌شوند.

### 6.4 عنوان محصول

برای هر محصول دو نسخه از عنوان نگه‌داری می‌شود:

| ستون | هدف |
|---|---|
| `product_title` | عنوان تمیزشده و قابل نمایش در Dashboard |
| `product_title_normalized` | نسخهٔ نرمال‌شده برای Matching، Business Key و Duplicate Detection |

### 6.5 نمونه

| مقدار خام | مقدار پاک‌سازی‌شده |
|---|---|
| ` گوشی  موبايل سامسونگ  ` | `گوشی موبایل سامسونگ` |
| `كابل شارژ  USB-C` | `کابل شارژ USB-C` |
| `موجود در انبار` | `موجود در انبار` |

## 7. نرمال‌سازی اعداد فارسی و عربی

### 7.1 مسئله

در فایل‌های ورودی، قیمت یا درصد ممکن است با رقم‌های فارسی یا عربی ثبت
شده باشد.

### 7.2 قانون

قبل از Parse شدن عدد، ارقام فارسی و عربی به ارقام انگلیسی تبدیل می‌شوند.

| رقم فارسی/عربی | رقم استاندارد |
|---|---|
| `۰` / `٠` | `0` |
| `۱` / `١` | `1` |
| `۲` / `٢` | `2` |
| `۳` / `٣` | `3` |
| `۴` / `٤` | `4` |
| `۵` / `٥` | `5` |
| `۶` / `٦` | `6` |
| `۷` / `٧` | `7` |
| `۸` / `٨` | `8` |
| `۹` / `٩` | `9` |

### 7.3 مثال

| مقدار خام | مقدار قابل تبدیل |
|---|---|
| `۱۵,۵۰۰,۰۰۰` | `15500000` |
| `٢٥٪` | `25` |
| `۱۲٫۵` | `12.5` |

## 8. پاک‌سازی و Parse کردن قیمت

### 8.1 هدف

قیمت‌ها باید از فرم‌های متنی، عددی یا ترکیبی به مقدار استاندارد عددی
تبدیل شوند تا امکان محاسبه، مقایسه، تشخیص Outlier و ذخیره‌سازی در
PostgreSQL فراهم شود.

نوع هدف برای قیمت‌ها در پایگاه داده:

```text
NUMERIC(30,2)
```

### 8.2 مراحل Parse کردن قیمت

فرآیند کلی Parse قیمت شامل مراحل زیر است:

1. تشخیص مقدار خالی و تبدیل آن به `NULL`.
2. تبدیل رقم‌های فارسی و عربی به ارقام انگلیسی.
3. حذف کلمات واحد پول، در صورت وجود.
4. حذف جداکننده‌های هزارگان مانند `,` و `٬`.
5. مدیریت جداکنندهٔ اعشار در صورت قابل تشخیص بودن.
6. حذف فاصله‌های غیرضروری.
7. تبدیل مقدار نهایی به عدد.
8. اعمال Contract واحد پول بر اساس Mapping منبع.
9. ثبت نتیجه در ستون `price` یا `old_price`.

### 8.3 نمونه‌های ورودی

| مقدار خام | مقدار عددی قبل از تبدیل واحد |
|---|---:|
| `1,250,000` | 1250000 |
| `۱٬۲۵۰٬۰۰۰` | 1250000 |
| `1,250,000 تومان` | 1250000 |
| `۱۲۵۰۰۰۰۰ ریال` | 12500000 |
| `ناموجود` | `NULL` |
| `-` | `NULL` |

### 8.4 قرارداد واحد پول

خروجی استاندارد پایپلاین در Batch موفق جاری با کد ارز زیر ذخیره شده است:

```text
IRR
```

قانون مفهومی تبدیل واحد:

| واحد اولیه | واحد مقصد | تبدیل |
|---|---|---:|
| Toman / تومان | IRR | ضرب در 10 |
| Rial / ریال | IRR | بدون تغییر |

### 8.5 نکتهٔ مهم دربارهٔ واحد پول

واحد پول هر منبع باید بر اساس Mapping و بررسی نمونه‌های واقعی همان منبع
تعیین شود. تبدیل تومان به ریال فقط زمانی اعمال می‌شود که مقدار یا Mapping
منبع نشان دهد قیمت بر حسب تومان ثبت شده است.

نباید تمام قیمت‌ها صرفاً با فرض تومان بودن در 10 ضرب شوند، زیرا باعث
ایجاد قیمت‌های غیرواقعی و Outlier می‌شود.

### 8.6 رفتار برای قیمت‌های نامعتبر

| وضعیت | مقدار ذخیره‌شده | نتیجهٔ Quality |
|---|---|---|
| قیمت خالی | `NULL` | `MISSING_PRICE` |
| قیمت صفر | `0` | `ZERO_PRICE` |
| قیمت منفی | مقدار عددی | `NEGATIVE_PRICE` در صورت اعمال Rule |
| متن غیرقابل Parse | `NULL` | معمولاً به‌عنوان قیمت مفقود یا Transform Note |
| قیمت بسیار غیرعادی | مقدار عددی حفظ می‌شود | `PRICE_OUTLIER` پس از تحلیل آماری |

قیمت صفر یا پرت در Raw و Staging حذف نمی‌شود. این مقادیر برای تحلیل کیفیت
داده نگه‌داری و Flag می‌شوند.

## 9. پاک‌سازی قیمت قبلی

ستون `old_price` نشان‌دهندهٔ قیمت قبلی، قیمت قبل از تخفیف یا قیمت مرجع
در منبع است.

قوانین پاک‌سازی `old_price` مشابه `price` هستند:

- تبدیل ارقام فارسی و عربی.
- حذف جداکننده‌ها.
- حذف برچسب واحد پول.
- تبدیل واحد در صورت لزوم.
- تبدیل مقدار خالی یا غیرقابل Parse به `NULL`.

### قانون اعتبار تجاری

اگر `old_price` کمتر از `price` باشد، این وضعیت به‌عنوان ناسازگاری ثبت
می‌شود:

```text
OLD_PRICE_LT_PRICE
```

این Rule الزاماً رکورد را حذف نمی‌کند؛ بلکه مشکل را در لایهٔ Audit ثبت
می‌کند.

در Batch 6 تعداد ثبت‌شده برای این Rule برابر با 428 مورد بود.

## 10. نرمال‌سازی درصد تخفیف و کش‌بک

فیلدهای زیر باید به مقدار درصدی استاندارد تبدیل شوند:

```text
discount_percent
cash_back_percent
```

نوع هدف در PostgreSQL:

```text
NUMERIC(5,2)
```

### 10.1 مراحل تبدیل

1. تشخیص مقدار خالی.
2. تبدیل ارقام فارسی و عربی.
3. حذف علامت `%` و `٪`.
4. حذف متن‌های اضافی مانند `درصد` در صورت وجود.
5. تبدیل مقدار قابل Parse به عدد.
6. استانداردسازی مقدار در بازهٔ 0 تا 100.
7. ثبت مقادیر خارج از بازه به‌عنوان Issue.

### 10.2 مثال

| مقدار خام | مقدار استاندارد |
|---|---:|
| `20%` | 20.00 |
| `۲۰٪` | 20.00 |
| `15` | 15.00 |
| `0.15` | بر اساس Contract تبدیل، در صورت تفسیر Fraction برابر 15.00 |
| `NULL` | `NULL` |

### 10.3 اعتبارسنجی بازه

مقدار درصد باید در بازهٔ زیر باشد:

```text
0 <= percent <= 100
```

در صورت خارج بودن مقدار از بازه، Rule زیر ثبت می‌شود:

```text
INVALID_PERCENTAGE
```

## 11. پاک‌سازی URL محصول و تصویر

### 11.1 هدف

URL محصول و تصویر باید به فرم قابل‌استفاده برای Dashboard یا API تبدیل
شود.

فیلدهای مربوط:

```text
product_url
image_url
```

### 11.2 قوانین URL

1. مقدار خالی به `NULL` تبدیل می‌شود.
2. فاصله‌های ابتدا و انتهای URL حذف می‌شوند.
3. اگر URL در قالب Markdown باشد، URL از ساختار Markdown استخراج می‌شود.
4. اگر یک سلول شامل چند URL باشد، مقدار قابل‌استفاده از آن استخراج می‌شود.
5. URL نامعتبر برای بررسی Data Quality Flag می‌شود.
6. URL باید با یکی از Prefixهای زیر آغاز شود:

```text
http://
https://
```

### 11.3 مثال Markdown

| مقدار خام | مقدار استاندارد |
|---|---|
| `[مشاهده محصول](https://example.com/p/1)` | `https://example.com/p/1` |
| ` https://example.com/p/1 ` | `https://example.com/p/1` |
| `بدون لینک` | `NULL` یا مقدار Flag‌شده |

### 11.4 Rule مربوط

برای URL نامعتبر، Rule زیر قابل ثبت است:

```text
INVALID_URL
```

## 12. استانداردسازی وضعیت موجودی

### 12.1 هدف

منابع مختلف ممکن است وضعیت موجودی را با عبارت‌های متفاوت ثبت کنند.
ستون خروجی استاندارد به شکل زیر است:

```text
is_available BOOLEAN
```

مقادیر ممکن:

```text
TRUE
FALSE
NULL
```

### 12.2 مقادیر قابل نگاشت به موجود

نمونه‌هایی از مقادیر قابل نگاشت به `TRUE`:

```text
موجود
موجود در انبار
available
in_stock
true
yes
1
```

### 12.3 مقادیر قابل نگاشت به ناموجود

نمونه‌هایی از مقادیر قابل نگاشت به `FALSE`:

```text
ناموجود
اتمام موجودی
تمام شده
unavailable
out_of_stock
false
no
0
```

### 12.4 وضعیت نامشخص

اگر مقدار خام خالی باشد یا با هیچ‌یک از Mappingهای شناخته‌شده تطابق
نداشته باشد، مقدار استاندارد برابر `NULL` خواهد بود.

در صورت وجود ستون یا مقدار نامعتبر مربوط به Availability، Rule زیر ثبت
می‌شود:

```text
INVALID_AVAILABILITY_COLUMN
```

در Batch 6 یک مورد از این Rule ثبت شد.

## 13. پاک‌سازی Brand، Category و Merchant

### 13.1 هدف

داده‌های برند، دسته‌بندی و فروشنده در منابع مختلف با تفاوت‌هایی در
بزرگ/کوچک بودن حروف، فاصله، کاراکتر فارسی/عربی و نوشتار ثبت می‌شوند.

برای جلوگیری از ایجاد Dimensionهای تکراری، مقادیر برای کلیدهای نرمال‌شده
آماده می‌شوند.

### 13.2 Brand

مقدار خام برند در Staging نگه‌داری می‌شود:

```text
brand_raw
```

هنگام بارگذاری Core، نام نرمال‌شده برای ایجاد یا Match کردن رکورد در
جدول زیر استفاده می‌شود:

```text
core.dim_brands
```

نمونهٔ نرمال‌سازی:

| مقدار خام | مقدار نرمال‌شده برای Match |
|---|---|
| `Samsung` | `samsung` |
| `SAMSUNG` | `samsung` |
| `سامسونگ` | `سامسونگ` |
| `  Apple ` | `apple` |

### 13.3 Category

مقدار خام دسته‌بندی در فیلد زیر نگه‌داری می‌شود:

```text
category_raw
```

نسخهٔ نرمال‌شده برای ایجاد یا Match کردن Category در جدول زیر استفاده
می‌شود:

```text
core.dim_categories
```

### 13.4 Merchant

مقدار خام فروشنده در فیلد زیر نگه‌داری می‌شود:

```text
merchant_name_raw
```

Merchant فقط زمانی در Core ایجاد یا Match می‌شود که منبع مقدار فروشندهٔ
قابل اتکا ارائه کند.

به همین دلیل `merchant_key` در جدول Fact می‌تواند `NULL` باشد. این رفتار
برای منابعی که فروشندهٔ مشخص ندارند یا دادهٔ Merchant ندارند، صحیح است
و نباید با مقدار ساختگی جایگزین شود.

### 13.5 نکته دربارهٔ Fuzzy Matching

این مستند فقط رفتارهای پیاده‌سازی‌شده در پروژه را توصیف می‌کند. تا زمانی
که استفاده از یک کتابخانه و منطق Fuzzy Matching در کد تأیید نشده باشد،
نباید ادعا شود که Brand، Category یا Merchant با Levenshtein Distance،
RapidFuzz یا روش مشابه ادغام شده‌اند.

در نسخهٔ فعلی، نرمال‌سازی متنی و کلیدهای نرمال‌شده مبنای اصلی Match کردن
Dimensionها هستند.

## 16. مدیریت خطا در Transform

خطای یک رکورد نباید کل Batch را متوقف کند.

رفتار مورد انتظار:

1. مقدار غیرقابل تبدیل به `NULL` تبدیل می‌شود.
2. وضعیت Transform و توضیحات در Staging ثبت می‌شود.
3. Ruleهای Validation برای ثبت Issue اجرا می‌شوند.
4. پردازش سایر رکوردهای فایل و Batch ادامه پیدا می‌کند.
5. خطای سطح Batch یا خطای دیتابیس در `raw.ingestion_batches` و
   `audit.etl_run_logs` قابل پیگیری است.

فیلدهای مرتبط در Staging:

```text
transform_status
transform_notes
```

## 18. ارتباط با Validation و Quality Rules

Cleaning و Validation دو مفهوم مرتبط ولی متفاوت هستند:

| مرحله | هدف |
|---|---|
| Cleaning | تبدیل مقدار خام به مقدار استاندارد |
| Transformation | تغییر ساختار و نوع داده برای مدل استاندارد |
| Validation | بررسی معتبر بودن مقدار استاندارد |
| Duplicate Detection | شناسایی رکوردهای مشابه یا تکراری |
| Outlier Detection | شناسایی قیمت‌های آماری غیرعادی |

نمونه:

- `"۱,۵۰۰,۰۰۰ تومان"` ابتدا Clean و به مقدار عددی IRR تبدیل می‌شود.
- اگر مقدار نهایی صفر باشد، Rule `ZERO_PRICE` ثبت می‌شود.
- اگر قیمت بسیار غیرعادی باشد، در مرحلهٔ Outlier Detection Flag می‌شود.
- اگر کلید منبع تکراری باشد، Rule `DUPLICATE_SOURCE_ID` ثبت می‌شود.

جزئیات Validation Rules در فایل زیر مستند می‌شوند:

```text
docs/validation_rules.md
```

## 20. محدودیت‌ها و موارد قابل بهبود

موارد زیر برای توسعهٔ نسخه‌های بعدی پیشنهاد می‌شوند:

- ثبت دقیق‌تر دلیل تبدیل ناموفق هر فیلد در `transform_notes`.
- اضافه کردن Data Quality Threshold برای هشدار در اجرای Batchهای آینده.
