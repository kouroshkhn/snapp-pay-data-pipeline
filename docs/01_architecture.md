# پایپلاین داده Snapp Pay — معماری داده

## ۱. هدف

پایپلاین داده Snapp Pay یک سامانه پردازش داده برای جمع‌آوری، پاکسازی، اعتبارسنجی،
تبدیل، مدل‌سازی و ارائه‌ی لیستینگ‌های محصولات تجارت الکترونیک است.

داده‌های خام شامل عنوان محصول، شناسه محصول، برند، دسته‌بندی، فروشنده، قیمت،
تخفیف، درصد بازگشت وجه (Cashback)، وضعیت موجودی و لینک محصول هستند.

این پایپلاین فایل‌های ناهمگون منابع مختلف را به داده‌ای استاندارد تبدیل می‌کند که
قابل مصرف توسط Query های تحلیلی، API و داشبوردهای مدیریتی است.

طراحی داشبورد و رابط کاربری خارج از محدوده این پروژه است. تمرکز پروژه روی لایه
داده و رابط‌های لازم برای تغذیه داشبورد است.

## ۲. زمینه کسب‌وکار

سامانه، داده محصول و قیمت را از چندین منبع تجارت الکترونیک دریافت می‌کند. هر
منبع ممکن است فرمت فایل، قرارداد نام‌گذاری ستون، واحد قیمت، انکودینگ متن، ساختار
فروشنده و کیفیت داده متفاوتی داشته باشد.

پایپلاین مسائل زیر را پوشش می‌دهد:

- رکوردهای تکراری محصول یا لیستینگ
- عنوان یا قیمت گم‌شده
- قیمت صفر، منفی یا غیرواقعی
- ناسازگاری کاراکترهای فارسی و عربی
- بازنمایی‌های مختلف وضعیت موجودی
- نام‌های ناسازگار برند، دسته‌بندی و فروشنده
- واحدهای قیمتی متفاوت مانند تومان و ریال
- لینک‌های گم‌شده یا نادرست
- فایل‌های منبع با ساختار و نام ستون‌های متفاوت

خروجی نهایی یک مدل رابطه‌ای تحلیلی همراه با flag های کیفیت و رکوردهای Audit
است. رکوردهای نامعتبر یا مشکوک به‌صورت خاموش از لایه‌های Raw و Staging حذف
نمی‌شوند.

## ۳. محدوده پروژه

### شامل می‌شود

- خواندن فایل‌های منبع CSV و XLSX
- ثبت هر Batch و هر فایل منبع در سامانه
- نگه‌داری رکوردهای خام به‌صورت JSONB
- استانداردسازی متن، قیمت، URL، وضعیت موجودی، درصدها و ارز
- اعتبارسنجی رکوردهای تبدیل‌شده
- تشخیص رکوردهای کاندید تکراری
- تشخیص داده‌های پرت قیمتی
- بارگذاری رکوردهای استانداردشده در PostgreSQL
- ساخت جداول ابعادی (Dimension) و Fact
- ثبت مسائل و متریک‌های کیفیت داده
- ساخت ایندکس برای الگوهای دسترسی متداول
- ساخت View های تحلیلی
- ارائه Query های SQL و توابع Python برای دسترسی به داده
- تولید متریک‌های تحلیلی در فرمت JSON

### شامل نمی‌شود

- پیاده‌سازی داشبورد یا رابط کاربری
- استقرار اپلیکیشن Flask یا Dash
- دریافت داده به‌صورت Real-time/Streaming
- زمان‌بندی و ارکستراسیون Production
- احراز هویت و مجوزدهی برای یک API عمومی
- اعلان‌های خودکار (Notifications)
- رابط کاربری برای Lineage در سطح فیلد

## ۴. جریان کلی پایپلاین

پایپلاین شامل مراحل زیر است:

```text
فایل‌های منبع
    |
    v
Extract
    |
    v
ذخیره‌سازی Raw
    |
    v
Transform و Clean
    |
    v
ذخیره‌سازی Staging
    |
    v
Validation
    |
    v
تشخیص رکوردهای تکراری
    |
    v
تشخیص داده پرت قیمتی
    |
    v
Audit و متریک‌های کیفیت
    |
    v
مدل ابعادی Core
    |
    v
View های تحلیلی و Query های داشبورد
    |
    v
مصرف توسط API یا داشبورد
```

### ۴.۱ Extract

مرحله Extract:

- فایل‌های پشتیبانی‌شده در پوشه `raw/` را شناسایی می‌کند
- فایل‌های CSV و XLSX را می‌خواند
- نگاشت ستون‌های اختصاصی هر منبع را اعمال می‌کند
- یک کد منبع (source code) و نام Dataset تخصیص می‌دهد
- رکورد اصلی را به‌صورت payload سازگار با JSON نگه می‌دارد
- هر فایل را در `raw.raw_file_registry` ثبت می‌کند
- هر رکورد را در `raw.raw_product_records` ثبت می‌کند

لایه Raw، منبع حقیقت (source of truth) برای بازپردازش و اهداف Audit است.

### ۴.۲ Transform

مرحله Transform، رکوردهای ناهمگون منابع را به ساختار استاندارد Staging تبدیل
می‌کند.

نمونه‌هایی از تبدیل‌ها:

- یکسان‌سازی کاراکترهای فارسی و عربی
- یکسان‌سازی فاصله‌ها (Whitespace)
- پارس عددی قیمت
- یکسان‌سازی واحد قیمت
- پاکسازی URL
- استانداردسازی وضعیت موجودی
- پارس درصد تخفیف و Cashback
- نرمال‌سازی عنوان محصول
- آماده‌سازی فیلدهای برند، دسته‌بندی و فروشنده

داده تبدیل‌شده در `staging.stg_product_listings` ذخیره می‌شود.

### ۴.۳ Validate

مرحله Validation، رکوردهای تبدیل‌شده را در برابر قوانین فیلد الزامی، نوع داده،
محدوده مقدار و قوانین کسب‌وکار بررسی می‌کند.

مسائل شناسایی‌شده در `audit.validation_issues` ذخیره می‌شوند.

پایپلاین مسائل را با سطوح Severity زیر دسته‌بندی می‌کند:

- `ERROR`
- `WARNING`
- `INFO`

پیاده‌سازی فعلی بیشتر رکوردهای مشکل‌دار را نگه می‌دارد و مسئله را به‌عنوان یک
مورد Audit ثبت می‌کند. رکوردهایی که خطای مسدودکننده (blocking error) دارند،
طبق قوانین بارگذاری، می‌توانند از لایه Core حذف شوند.

### ۴.۴ تشخیص کیفیت (Quality Detection)

مرحله Quality دو تحلیل اضافه انجام می‌دهد:

- تشخیص رکورد کاندید تکراری
- تشخیص آماری داده پرت قیمتی

رکوردهای تکراری و پرت flag می‌خورند، نه اینکه فیزیکی از Raw یا Staging حذف
بشن.

flag های نتیجه در جدول Fact لایه Core در دسترس‌ان:

- `is_duplicate_candidate`
- `is_price_outlier`

### ۴.۵ Load

مرحله Load:

- Batch جدید را می‌سازد یا به‌روزرسانی می‌کند
- فایل‌ها و رکوردهای خام را درج می‌کند
- رکوردهای استانداردشده Staging را درج می‌کند
- Dimension ها را Upsert می‌کند
- رکوردهای Fact پذیرفته‌شده را درج می‌کند
- اطلاعات Validation و Quality را ذخیره می‌کند
- وضعیت Batch و تعداد ردیف‌ها را به‌روزرسانی می‌کند
- اطلاعات اجرای ETL را ثبت می‌کند

لایه Core رکوردهایی که شرایط لازم برای یک لیستینگ محصول قابل‌استفاده را ندارند
حذف می‌کند، در حالی که رکوردهای مشکوک ولی از نظر ساختاری معتبر ممکن است با
flag های کیفیت در Core باقی بمانند.

### ۴.۶ Analytics و مصرف داده

لایه Analytics ارائه می‌دهد:

- View های SQL برای دسترسی تحلیلی تکرارشونده
- خلاصه در سطح منبع
- دسترسی به لیستینگ محصول همراه با ویژگی‌های Dimension
- متریک‌های کیفیت
- آمار برند و دسته‌بندی
- خلاصه مسائل Validation
- Query های SQL مخصوص داشبورد
- متریک‌های JSON تولیدشده توسط Python

این پروژه شامل یک API مستقر Flask یا Dash نیست. با این حال، View های دیتابیس،
Query های SQL و توابع دسترسی Python، زیرساخت لازم برای چنین API ای را فراهم
می‌کنند.

## ۵. معماری پایگاه داده

پایگاه داده به پنج Schema منطقی تقسیم می‌شود:

| Schema | هدف | مسئولیت اصلی |
|---|---|---|
| `raw` | نگه‌داری منبع و ردیابی Batch | ذخیره متادیتای Ingestion و payload اصلی |
| `staging` | داده میانی استانداردشده | ذخیره لیستینگ‌های پاکسازی‌شده و تایپ‌شده |
| `core` | مدل رابطه‌ای تحلیلی | ذخیره Dimension ها و لیستینگ‌های Fact |
| `audit` | پایش کیفیت و اجرا | ذخیره مسائل، متریک‌ها و لاگ‌های ETL |
| `analytics` | لایه مصرف | ارائه View های تحلیلی |

## ۶. لایه Raw

### ۶.۱ `raw.ingestion_batches`

هر اجرای پایپلاین را ردیابی می‌کند.

فیلدهای مهم:

- `batch_id`
- `pipeline_name`
- `pipeline_version`
- `run_status`
- `started_at`
- `finished_at`
- `source_file_count`
- `records_extracted`
- `records_loaded_staging`
- `records_loaded_core`
- `error_message`

یک Batch ممکن است یکی از وضعیت‌های زیر را داشته باشد:

- `RUNNING`
- `SUCCESS`
- `FAILED`
- `PARTIAL`

### ۶.۲ `raw.raw_file_registry`

متادیتای هر فایل ورودی را ذخیره می‌کند:

- نام فایل اصلی
- مسیر فایل
- حجم فایل
- هش SHA-256
- فرمت فایل
- شناسه Batch
- وضعیت پردازش
- تعداد ردیف استخراج‌شده
- زمان پردازش
- پیام خطا (در صورت وجود)

### ۶.۳ `raw.raw_product_records`

هر ردیف استخراج‌شده از منبع را ذخیره می‌کند.

ستون `raw_payload` رکورد اصلی را به‌صورت JSONB نگه می‌دارد. این کار به تیم اجازه
می‌دهد مقادیر اصلی را بررسی کند و بدون وابستگی صرف به نمایش تبدیل‌شده، داده را
بازپردازش کند.

## ۷. لایه Staging

### ۷.۱ `staging.stg_product_listings`

این جدول یک بازنمایی استاندارد واحد برای لیستینگ‌های همه منابع دارد.

لایه Staging شامل:

- شناسه‌های منبع و Dataset
- شناسه محصول در منبع
- عنوان پاکسازی‌شده محصول
- عنوان نرمال‌شده محصول
- مقادیر خام برند و دسته‌بندی
- مقدار خام فروشنده
- قیمت فعلی و قبلی
- درصدهای Cashback و تخفیف
- وضعیت موجودی خام و استانداردشده
- URL محصول و تصویر
- واحد قیمت اصلی
- کد استاندارد ارز
- وضعیت تبدیل
- یادداشت‌های تبدیل

همه قیمت‌های بارگذاری‌شده در فیلدهای استاندارد قیمت، از قرارداد ارزی پیکربندی‌شده
پایپلاین استفاده می‌کنند. در خروجی Batch 6 موفق، کد ارز ذخیره‌شده `IRR` بود.

## ۸. لایه Core

لایه Core از یک مدل ابعادی (Dimensional Model) شامل Dimension ها و یک جدول
اصلی Fact پیروی می‌کند.

### ۸.۱ جداول Dimension

| جدول | هدف |
|---|---|
| `core.dim_sources` | فهرست اصلی سیستم‌های منبع |
| `core.dim_products` | هویت محصول و ویژگی‌های سطح محصول |
| `core.dim_brands` | مقادیر نرمال‌شده برند |
| `core.dim_categories` | دسته‌بندی‌های نرمال‌شده و سلسله‌مراتب دسته‌بندی |
| `core.dim_merchants` | هویت فروشنده |

### ۸.۲ جدول Fact

`core.fact_product_listings` مشاهدات لیستینگ محصول را ذخیره می‌کند.

فیلدهای مهم:

- `listing_id`
- `batch_id`
- `product_key`
- `merchant_key`
- `source_listing_id`
- `price`
- `old_price`
- `cash_back_percent`
- `discount_percent`
- `is_available`
- `validation_status`
- `is_duplicate_candidate`
- `is_price_outlier`
- `currency_code`
- `observed_at`
- `loaded_at`

جدول Fact، جدول اصلی مورد استفاده برای تحلیل قیمت، موجودی، منبع، فروشنده، برند
و دسته‌بندی است.

## ۱۰. مدل کیفیت داده

پایپلاین از رویکرد Flag-and-Audit پیروی می‌کند:

۱. نگه‌داری رکورد اصلی در Raw
۲. نگه‌داری بازنمایی استانداردشده در Staging
۳. ثبت مسائل شناسایی‌شده در لایه Audit
۴. حذف فقط رکوردهایی که نمی‌توانند به‌طور ایمن در Core استفاده شوند
۵. نگه‌داری رکوردهای مشکوک ولی از نظر ساختاری قابل‌استفاده، همراه با flag

خروجی Batch 6 موفق نتایج زیر را تولید کرد:

| متریک | مقدار |
|---|---:|
| رکوردهای Raw | 1,187,166 |
| رکوردهای Staging | 1,187,166 |
| لیستینگ‌های Fact در Core | 1,018,098 |
| محصولات | 642,600 |
| فروشندگان | 3,527 |
| برندها | 2,101 |
| دسته‌بندی‌ها | 1,886 |
| مسائل Validation | 431,556 |

جدول Fact در Core شامل شاخص‌های کیفیتی است که به مصرف‌کنندگان اجازه می‌دهد بین
دیتاست کامل و زیرمجموعه سخت‌گیرانه‌تر تحلیلی یکی را انتخاب کنند.

## ۱۱. لایه Analytics

Schema به نام `analytics` شامل شش View است:

| View | هدف |
|---|---|
| `analytics.vw_product_listings` | دسترسی غیرنرمال به لیستینگ همراه با Dimension ها |
| `analytics.vw_source_summary` | آمار لیستینگ و قیمت در سطح منبع |
| `analytics.vw_quality_metrics` | متریک‌های کیفیت به تفکیک منبع |
| `analytics.vw_issue_summary` | تعداد مسائل به تفکیک قانون و Severity |
| `analytics.vw_brand_stats` | آمار لیستینگ و قیمت به تفکیک برند |
| `analytics.vw_category_stats` | آمار لیستینگ و قیمت به تفکیک دسته‌بندی |

این View ها یک قرارداد دسترسی پایدار برای یک API یا داشبورد آینده فراهم می‌کنند.

نمونه:

```sql
SELECT
    source_code,
    source_name,
    total_listings,
    distinct_products,
    avg_price_excl_outliers,
    median_price
FROM analytics.vw_source_summary
ORDER BY total_listings DESC;
```

## ۱۲. طراحی عملکرد (Performance)

پروژه شامل ایندکس‌هایی برای موارد زیر است:

- فیلتر Batch
- Join محصول
- Join فروشنده
- وضعیت Validation
- فیلتر قیمت
- flag تکراری
- flag پرت (Outlier)
- فیلتر منبع
- Lookup ابعاد (Dimension)
- بازیابی مسائل Audit
- ارتباط Raw به Staging

فایل اسکریپت ایندکس در مسیر زیر قرار دارد:

```text
sql/04_create_indexes.sql
```

بررسی دیتابیس پس از ساخت ایندکس‌ها، وجود ایندکس در جداول اصلی Raw، Staging،
Core و Audit را نشان داد.

نتیجه‌گیری‌های عملکردی باید بر اساس خروجی واقعی `EXPLAIN ANALYZE` باشند. زمان
اجرای Query نباید به‌عنوان مقدار اندازه‌گیری‌شده ارائه شود، مگر اینکه واقعاً از
محیط PostgreSQL هدف ثبت شده باشد.

## ۱۵. محدودیت‌های شناخته‌شده

موارد زیر باید قبل از ارائه پروژه به‌عنوان یک سامانه Production بررسی و تأیید
شوند:

- تأیید معنای دقیق واحد ارز برای هر منبع
- تأیید اینکه هر Reader اختصاصی هر منبع و مسیر Fallback آن مستند شده باشد
- اجرا و ثبت نتایج واقعی `EXPLAIN ANALYZE` برای Query های نماینده
- بازبینی قیمت‌های فوق‌العاده (Extreme) پیش از استفاده در KPI های کسب‌وکاری
- تأیید اینکه همه نام ستون‌های SQL در مستندات، با Schema مستقرشده مطابقت دارند
- افزودن یک Endpoint در Flask یا Dash فقط در صورتی که تحویل پروژه نیازمند یک
  API قابل‌اجرا باشد
- تأیید اینکه تعداد قوانین Validation مستندشده، دقیقاً با قوانین پیاده‌سازی‌شده در
  کد فعلی مطابقت دارد

آخرین Batch باید با Query زیر بررسی شود:

```sql
SELECT
    batch_id,
    run_status,
    started_at,
    finished_at,
    source_file_count,
    records_extracted,
    records_loaded_staging,
    records_loaded_core,
    error_message
FROM raw.ingestion_batches
ORDER BY batch_id DESC
LIMIT 1;
```
